# Product UI decision

2026-11-03. Applied user skill `C:/Users/MOHD/.agents/skills/geist-nextjs-design/SKILL.md` after the user's updated design instructions. The application keeps the MOHD delivery product identity; it does not reproduce Vercel branding or claim pixel-perfect Geist fidelity.

The layout is an operations product: persistent navigation, eight delivery views, a compact table and contextual delivery panel. Primary actions live next to their records. Neutral surfaces, thin borders, an 8 px radius, restrained shadows and a 4 px spacing scale establish hierarchy. Status colors communicate success/warning/error alongside text. Delivery source state remains separate from work progress.

Tailwind CSS 4 is the primary styling engine. `globals.css` defines semantic tokens and composes the product's reusable classes through Tailwind `@apply`; component primitives use utility classes directly. Imperative CSS is limited to token values, time-axis geometry, responsive table/calendar constraints and appropriate media queries. Geist Sans and Geist Mono are self-hosted by the installed `geist` package/Next font integration; builds do not request Google Fonts. Mono is reserved for identifiers, times and technical details.

Local shadcn-style Button/Input/Card/Dialog source is editable and uses the same tokens. `components.json` documents aliases and the Tailwind v4 setup. Dialog relies on Radix focus scopes, Escape handling, outside interaction protection and explicit focus restoration. Native labels/selects/checkboxes retain browser semantics; checkbox groups use fieldset/legend. No second component library is used.

Light and dark define matching background/foreground, card, popover, primary, secondary, muted, accent, border, input, ring and destructive roles. `next-themes` persists only the theme preference, supports system changes and applies the class before paint. The selector renders a stable system placeholder until the client mounts. The single HTML `suppressHydrationWarning` covers this documented theme-class difference; it does not suppress TypeScript, lint, business or API checks.

Text token pairs use readable contrast (ordinary foreground and muted text target at least 4.5:1), visible focus and labelled icon actions. The application respects reduced motion and does not disable zoom. Dense tables and the calendar have their own horizontal scrolling; normal forms and panels reflow to a single column. These implementation decisions do not constitute a WCAG certification or comprehensive accessibility audit.

Native scrollbars share neutral light/dark thumb tokens across the viewport and nested scroll containers, including tables, dialogs, calendar, code blocks and textareas. Chromium/WebKit uses a 10 px track with rounded, inset thumbs and distinct hover/active colors; the Firefox standards fallback keeps a native thin scrollbar with matching colors rather than promising identical geometry. Custom styling is scoped to `forced-colors: none`, preserving browser/OS high-contrast scrollbars. Scrolling, overflow, gutters, keyboard behavior and textarea resizing remain native; no JavaScript wrapper or dependency was added. The feature split avoids the standards properties overriding WebKit pseudo-element styling, as described in [Chrome's scrollbar guidance](https://developer.chrome.com/docs/css-ui/scrollbar-styling).

Calendar columns use elapsed minutes since each Europe/Rome midnight, not naive wall-clock subtraction. A fall-back day has 25 hours, spring-forward has 23. Daily hour labels include offsets on transition dates; visit timestamps always include their Rome UTC offset. The 45-minute visit `2026-10-25T02:45+02:00 → 02:30+01:00` remains visible and is covered by a regression test.

Booking and rescheduling use native date-and-time controls for Starts at / Ends at, with an explicit Europe/Rome label. Operators enter local wall time; hidden API fields contain canonical UTC ISO instants independently of the computer timezone. Spring gaps and impossible dates block submission. Fall folds require an explicit first/second occurrence with its UTC offset; rescheduling preselects the stored occurrence and retains seconds/milliseconds. Background Refresh keeps the mounted controls, draft and scroll, with the existing explicit latest-data action for stale revisions.

Validation is independent of appearance. Backend mutations are acknowledged only after their known Zod response contract passes; quantities and completion reasons come from the backend. Changing theme, layout or directories does not change domain authorization.

Refresh is a background data operation. Loading placeholders are reserved for the first load; existing content stays mounted, and entity keys use stable IDs rather than server revisions. Small status regions keep their space while requests run or fail. Drafts, expanded sections, tabs and scroll positions remain intact. A refreshed revision cannot silently grant an old draft permission to overwrite newer data: the operator explicitly loads current values for that form. Aborted/stale GETs cannot overwrite a newer request or a successful mutation. Real-component DOM regressions verify these invariants with deferred HTTP fixtures.
