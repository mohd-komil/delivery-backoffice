# Delivery Crew — локальный фронтофис

## Рейсы и возвращение — 11 ноября 2026

Добавлены **My routes** и карточка опубликованного рейса с очередью остановок, точными строками работ, машиной, водителем, ответственным и сохранённым въездом. Самостоятельные визиты остаются в **My visits**. Выезд, начало возвращения и фактический возврат — разные действия с проверкой прав на backend. Возврат не заменяет отчёт остановки и приёмку груза складом. Refresh сохраняет введённую заметку. [Контракты, проверки и отдельный тестовый запуск](docs/route-execution.md).

Проверены typecheck, typed lint, **41/41 тестов** и production build. В Chrome при ширине 390 px проверены выезд, блокировки Start, переход к возвращению и фактический возврат; Refresh сохраняет вкладку, заметку и подтверждающий флажок. Вернувшийся рейс попадает в History, завершённые визиты — в Past visits. Для продолжения того же отдельного демо используйте backend harness с `--resume`; обычный запуск без этого флага создаёт новую учебную схему. Физические телефоны в этой проверке не использовались.

## Причины невыполненных работ — 10 ноября 2026

В Finish visit для каждой запланированной операции с фактом меньше плана нужна причина. Для «Другое» обязательно объяснение; заметки ограничены 500 символами. Доставка, установка и забор различаются по строке заказа, даже если SKU совпадают. При полном выполнении причина скрывается и не отправляется. Изменение данных после подписания требует новых подписей; обычный Refresh сохраняет открытый черновик.

Проверки: typecheck, typed lint, **28/28 тестов** и production build. В Chrome отправлен [учебный отчёт DEMO/REASONS/0001](http://127.0.0.1:3002/visits/1f965258-fba2-4107-930a-eff220069320) с четырьмя причинами, фото и двумя учебными подписями. Проверены обязательная причина, пояснение Other, сохранение черновика при Refresh и ширина 390 px. Физические телефоны не проверялись. [Сценарий, остатки и History](../backoffice-backend/docs/demo-work-reasons.md).

## План работ визита — 10 ноября 2026

В карточке появился **Work for this visit**: плановые количества доставки, установки и забора по каждой строке заказа. Весь товарный контекст остаётся видимым; строки вне плана помечаются **Not planned for this visit** и не получают ввод фактических количеств. Backend отклоняет превышение плана и не смешивает одинаковые SKU из разных заказов.

Start visit требует подтверждения клиента, проверенного состава работ и достаточного количества товара у клиента либо доставки этого количества в том же визите. Старые визиты без плана требуют явной проверки диспетчером. Сборка, ожидающая ранее запланированную доставку, помечается отдельно. Подтверждение наличия товара для услуги «только установка» не создаёт фиктивную доставку.

Проверка: typecheck, typed lint, **21/21 тестов** и production build прошли. В Chrome проверен повторный визит [DEMO/GIANLUCA/0001](http://127.0.0.1:3002/visits/8cb84445-1eee-46d2-be19-270f9f91135c): по заказу 9201 довоз 1 и установка 2; заказ 9202 того же SKU выполнен и вне плана. Проверен мобильный viewport 390 px; физический телефон и камера в этом этапе не проверялись. Подробности: [демонстрация и правила](../backoffice-frontend/docs/visit-work-scope.md).

Отдельное Next.js приложение для бригад. Подключается по HTTP к общему NestJS backend. Для входа нужны логин и пароль действующего участника, заданные в Backoffice → Participants. Вымышленные учётные данные для локального стенда хранятся в игнорируемом `backoffice-backend/.local/participant-demo-accounts.json`. Аккаунт администратора или оператора используется только в backoffice.

Из корня проекта:

```powershell
Set-Location backoffice-backend
docker compose up -d --build backend
Set-Location ../crew-frontend
npm ci
npm run verify
npm start
```

Откройте [http://127.0.0.1:3002](http://127.0.0.1:3002). `npm run dev` использует тот же адрес. Backend слушает `127.0.0.1:3001`. Если нужен другой разрешённый адрес локального API, скопируйте `.env.example` в `.env.local`. Для входа используйте один и тот же host из настройки backend `CREW_FRONTEND_ORIGIN`; по умолчанию это `http://127.0.0.1:3002`.

На учебном стенде войдите как Simone Lo Presti (`simone.lopresti.demo@example.test`) с паролем из указанного выше локального файла. `DEMO/OUT/0006` ожидает подтверждения, `DEMO/OUT/0007` готов к старту. В `DEMO/OUT/0008` проверены запуск, отметка чек-листа и проблема с PNG. В `DEMO/OUT/0009` сохранён общий частичный итог по Catania Uno и Messina Due, который отправил Simone. В `DEMO/OUT/0011` сохранён учебный итог с двумя нарисованными подписями. Его можно посмотреть в Backoffice → Partially completed → History. Доставка готова к ручному закрытию. Завершённые визиты сразу переходят в Past visits, даже если их плановое время ещё впереди.

- **Мои визиты:** фактические назначения на сегодня и предстоящие даты в Europe/Rome. Обычный состав бригады сам по себе не даёт доступ.
- **Карточка визита** показывает адрес, контакт, инструкции, товары, назначенные задачи и статус согласия клиента. После подтверждения доступен Start visit. В работе можно отмечать и снимать отметки по чек-листу своей бригады и сообщить о проблеме, приложив один JPEG или PNG до 5 МиБ. Фото открывается в backoffice из Issues & returns. Отмеченные пункты видны в History.
- **Finish visit** доступен одному ответственному, которого Франческа или администратор выбирает из фактического состава в Backoffice → Visits & tasks. После начала визита форма находится в блоке Visit work in progress на вкладках Visits & tasks и Overview. Ответственный заполняет общий итог и фактически доставленное количество по строкам. Все участники продолжают отмечать задачи своих бригад. После отправки Backoffice → History показывает итог с отметками обеих бригад, временем работы и автором. Частичный итог завершает визит, а оставшиеся количества, задачи и подписи учитываются отдельно при закрытии доставки.
- **Подписи при завершении** обязательны для нового итога из Crew. Клиент или получатель вводит имя и расписывается в своей области. Имя ответственного берётся из назначения, а он расписывается во второй области. Обе области поддерживают палец, стилус и мышь, каждую можно очистить отдельно. Если подписываемые данные изменились, обе подписи нужно поставить заново. Франческа видит рисунки, имена и время записи в History рядом с итогом визита.
- **Фото выполнения** обязательны при Finish visit. Снимите фото камерой или выберите несколько в галерее. Поддерживаются 1–100 JPEG или PNG до 5 МиБ каждый и до 20 МиБ суммарно. Можно удалить лишние кадры перед отправкой. При изменении набора фото обе подписи нужно поставить заново. Результат с двумя учебными снимками доступен в Backoffice → Partially completed → DEMO/OUT/0013 → History → Completion photos.
- **Customer absent** доступно ответственному после Start visit, если ничего не передали и работы не выполнялись. Укажите причину и нажмите End visit without delivery. Визит перейдёт в Past visits. Причина, автор и время будут в Backoffice → History, а весь остаток останется доступен для повторного визита.
- **PWA:** манифест, обычные и maskable иконки, standalone запуск. Для проверки установки используйте сборку (`npm run build`, `npm start`). Локальный loopback считается доверенным контекстом в поддерживающих браузерах. На реальном телефоне нужен доступный HTTPS-стенд; loopback компьютера с телефона недоступен. Service worker показывает только публичный экран обрыва связи и не сохраняет страницы, контакты или ответы API. В обычном браузере приложение работает без установки.

Маршруты расположены в `src/app`, рабочие экраны — в `src/_pages`, общие элементы и проверяемые HTTP-контракты — в `src/shared`. Прокси `src/_app/crew-api` обслуживает явно разрешённые crew-методы и пути, передаёт crew-сессию и отключает кэширование. Backend проверяет актуальное назначение и версию доставки. Повтор неизменённого запроса использует прежний идентификатор, а Refresh и конфликт версии сохраняют черновик открытой формы.

Обновление 2026-11-11: в каждой плановой строке Finish visit доступны камера и выбор фото с уже заданной привязкой к строке заказа. Лимиты 100 фото / 20 МиБ общие для всего отчёта. Два одинаковых SKU из разных заказов сохраняют независимые фото, причины и проблемы. Для Problem можно выбрать категорию и уже зарегистрированную проблему этой строки, чтобы сообщить о том же случае без нового Issue. Изменение фото, категории или ссылки на проблему требует новых подписей.

Инструкции и чертежи в карточке строки показывают записанную версию, дату, источник и автора. Общие документы доставки отображаются отдельно. Новая версия файла не изменяет прежние байты; History в Backoffice показывает версии, доступные при отправке отчёта. Для старых документов отсутствующие тип, версия и источник явно обозначаются как неизвестные. Все ссылки требуют действующего назначения на визит; приватные документы не кешируются PWA. Для этого обновления прошли `npm run typecheck`, `npm run lint`, все 33 теста и `npm run build`. Новые миниатюры и загрузка с телефона требуют отдельной проверки в браузере/на физическом устройстве.

`npm run verify` прошёл типизацию, typed lint, 13 тестов и сборку. Третий этап проверен в Chrome на двух бригадах и с чтением результата в Backoffice. Второй участник сохранил свою отметку через локальный API и получил 403 при отправке общего итога. Refresh сохранил черновик ответственного. В Chrome проверена форма подписей, предупреждение при отсутствии фото и отображение двух сохранённых миниатюр в History. Сохранение учебных подписей и фото проверено через локальный HTTP API. Сенсорный ввод, камера и установка на физических Android/iPhone остаются проверками для доступного им HTTPS-стенда.

Повреждение, обнаруженное во время начатого визита, не скрывает Finish visit у назначенного ответственного. Блокировка готовности запрещает старт следующих забронированных визитов; остальные причины пересмотра плана сохраняют силу. Это проверено через Nest HTTP на изолированной PostgreSQL и через контракт/локализованное уведомление Crew.
